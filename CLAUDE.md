# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Working Precision (make no mistakes)

Default to maximum precision and self-verification on every task:
- Verify facts, file contents, symbols, and API signatures against the source before acting — don't rely on memory or assumption.
- Mentally test code and re-derive any calculation before committing to it.
- State uncertainty explicitly rather than guessing; prefer accuracy over speed.
- Preserve behavior exactly when refactoring unless a change is the explicit goal.

## Build Commands

```bash
# Generate Visual Studio 2022 solution
premake5 vs2022

# Build from command line (after generating solution)
msbuild VFEngine/VertexForge.sln /p:Configuration=Development /p:Platform=x64
msbuild VFEngine/VertexForge.sln /p:Configuration=Debug /p:Platform=x64
msbuild VFEngine/VertexForge.sln /p:Configuration=Release /p:Platform=x64

# Build a single project (faster iteration)
msbuild VFEngine/VertexForge.sln /t:Editor /p:Configuration=Development /p:Platform=x64
msbuild VFEngine/VertexForge.sln /t:Tests  /p:Configuration=Debug /p:Platform=x64
```

**Configurations** (`vfStandardConfigs` in `premake5.lua`):
- **Debug** — `DEBUG`, symbols, no optimization. Adds `JPH_ENABLE_ASSERTS` (Jolt) and `VF_ENABLE_VALIDATION` (Vulkan validation layers).
- **Development** — the day-to-day play-test build. Optimized (`/O2`, `NDEBUG`) **with** debug symbols, plus `VF_DEVELOPMENT` for editor-only niceties. Vulkan validation stays ON (user preference; see the `Development` filter on Graphics) but Jolt asserts are OFF.
- **Release** — `NDEBUG`, optimized, no validation, no asserts.

Note the Editor stays a `ConsoleApp` in all three configs (console logs always visible — user preference). Shipped games are built by GameExport from Runtime, not by switching the Editor config.

**Prerequisites**: Vulkan SDK installed with `VULKAN_SDK` environment variable set.

**Toolchain**: C++20, MSVC toolset `v145` (VS2026), latest Windows SDK. Global flags `/utf-8 /MP /bigobj` (`/bigobj` because some TUs — e.g. `HierarchyService.cpp`, Tests — exceed the default COFF section limit instantiating templates over the full component inventory). Engine-wide defines: `VULKAN_HPP_DISPATCH_LOADER_DYNAMIC=1`, `GLM_FORCE_DEPTH_ZERO_TO_ONE` (Vulkan [0,1] depth range).

**Output**: Executables in `bin/Editor/<Config>/x64/`, `bin/Runtime/<Config>/x64/`, `bin/Tests/<Config>/x64/`. Each SharedLib subsystem also lands in `bin/<Subsystem>/<Config>/x64/` and is copied into Editor/Runtime/Tests output dirs via `postbuildcommands`.

## Tests

The `Tests` project (`VFEngine/tests/`) is a doctest-based CPU-only unit test runner — no rendering dependencies. Each `test_*.cpp` registers its own `TEST_CASE`s.

```bash
# Run the full suite
bin/Tests/Debug/x64/Tests.exe

# List / filter (doctest CLI)
bin/Tests/Debug/x64/Tests.exe --list-test-cases
bin/Tests/Debug/x64/Tests.exe --test-case="*terrain*"
bin/Tests/Debug/x64/Tests.exe --source-file="*test_terrain*"
bin/Tests/Debug/x64/Tests.exe --subcase="boundary stitching"
```

Add new tests by dropping a `test_<feature>.cpp` into `VFEngine/tests/` — premake globs it automatically. `main.cpp` is the doctest entry point; do not add a second.

## Architecture

### Module Dependency Graph

```
Editor   ──> Services, Import, Core, Plugin, Mcp, ProceduralGen, ImageProcessing, GameExport, ECSRegistry (ONLY)
Import   ──> Utilities (SharedLib/DLL, requires CMake-built libs: assimp, freetype, libogg, libvorbis)
Runtime  ──> Services, Core (ONLY)
Services ──> Utilities, Terrain, Serialization, World, Window
Core     ──> Graphics, Audio, Physics, Animation, mType, jolt, recast
Graphics ──> Window, VFX, imgui
Plugin   ──> Services, Utilities (engine-side plugin SDK + loader)
Mcp      ──> Services, Import, Utilities (MCP server for AI agents; NO Core/Graphics/ImGui)
```

**Premake groups**: `Engine` (Editor, Runtime, Core, Graphics, Window, Import, Services, Plugin, Mcp, Utilities), `Subsystems` (extracted modules — see table below), `libs` (vendored third-party), `Plugins` (sample/external plugin DLLs under `plugins/`).

Module kinds: Editor/Runtime/Tests are `ConsoleApp`. Most modules are `StaticLib`. `SharedLib/DLL`: Import, Audio, Animation, Terrain, World, Serialization, ProceduralGen, ImageProcessing, GameExport, ECSRegistry, jolt, meshoptimizer, and external plugins.

### Key Patterns

- **Provider Interfaces** (in `services/providers/`): Abstract interfaces that define engine capabilities. Core implements these via adapters.
- **Adapters** (in `core/adapters/`): Implement provider interfaces by wrapping Core/Graphics controllers. Enable dependency inversion.
- **Bootstrap** (in `core/bootstrap/`): Initialize Core/Graphics and create adapters. `EditorBootstrap` and `RuntimeBootstrap` encapsulate startup.
- **Controllers** (in `*/controllers/`): Internal facade interfaces within Core/Graphics. Not exposed to Editor/Runtime.
- **Handlers**: Internal orchestrators that coordinate subsystems within a module.
- **ECS**: EnTT-based. Entities wrap `entt::entity` handles; components defined in `utilities/components/Components.hpp`.
- **Async Resources**: `ResourceManager` loads assets via `std::async`, returns futures.
- **Event System**: `EventDispatcher` singleton for decoupled communication via CQRS pattern (see Services Layer below).
- **DLSS inputs** (VK-1662, `graphics/render/upscaling/TemporalUpscaleMath.hpp`):
  - **Motion vectors** are `previous − current` in NDC (+y down). They are built on the graphics queue in the Upscale pass from THIS frame's depth, with UNJITTERED matrices (camera-relative clip→clip, composed in double). Streamline gets `motionVectorsJittered = false` and `mvecScale = 0.5` (NDC→UV).
  - **Jitter:** `JitterSequence::applyJitter` moves the image by exactly `+jitterOffset` render px for perspective and ortho, using DLSS's `8·(display/render)²` Halton phases.
  - **Streamline matrices** are jitter-free and a straight copy of GLM memory (row-vector + row-major): never transpose.
  - The GLSL convention lives in `resources/shaders/common/motion_vectors.glsl`; its CPU twin is tested by `test_upscale_motion_vectors`.
  - **Exposure** (VK-1663/1664): DLSS-SR reads the engine exposure (`useAutoExposure = eFalse`). The 1x1 R32F `kBufferTypeExposure` texel is `sanitizeExposure(PostProcessPipeline::getTonemapExposure())` (`graphics/render/postprocess/ExposureMath.hpp`): the LINEAR multiplier the tonemapper applies this frame.
    - Streamline reads `useAutoExposure` only when it creates the NGX feature, so keep it a constant. `preExposure`/`exposureScale` stay 1 (the colour is not pre-exposed). Only presets J/K read the texel; every mode uses K.
    - Auto exposure is ONE chain (`AutoExposureBuffer::state`); the CPU reads the copy written two frames back. Pinned by `test_upscale_exposure` and `test_auto_exposure`.
    - It adapts over REAL time: the effect's own `steady_clock` delta between steps, capped at 0.5 s (`clampAdaptationDelta`). Never use the camera time; the Runtime's is scaled gameplay time (VK-992). `adaptSpeedUp` applies when the scene gets brighter (the exposure falls) and `adaptSpeedDown` when it gets darker (VK-1670). The histogram binning and the reduce math have CPU twins in `ExposureMath.hpp` (decode with 254; the percentile window is at least one pixel wide), and string guards keep the GLSL identical.

**Editor launch contract** (VK-1682; `Main.cpp` header, helpers in `utilities/launch/`, launcher twin `launcher/.../service/EditorExitCode.java`, pinned by `test_editor_launch`):
- **Command line:** `Editor.exe [project.vfproj] [--launch-status <file>] [--mcp] [--mcp-port <n>] [--mcp-token <t>] [--console]`. Parsing is strict. `--console` (VK-1683) makes an editor started without a console window (the launcher: Java adds `CREATE_NO_WINDOW`) open its own (`FreeConsole` + `AllocConsoleWithOptions(NEW_WINDOW)`, else `AllocConsole`) and mirror its redirected stdout file into it (`utilities/launch/EditorConsole`); the std handles stay the log file, Ctrl+C/Break are ignored, closing the window ends the editor with `0xC000013A`. `main` first unbuffers stdout/stderr when they are redirected (`prepareStandardStreams`), so a crash loses no output.
- **Exit codes:** 0 normal, 2 bad arguments, 3 the `.vfproj` failed to load, 4 its schema MAJOR is newer than this editor, 5 another editor holds the project. The argument, `.vfproj` and lock checks run before the main window opens (the `EditorHandler` constructor creates it); a load that still fails after `init()` also exits 3. A crash exits with its exception code.
- **`--launch-status`:** one atomic JSON line `{state: loading|ready|failed, code, message, pid, crashDir}` (`crashDir`, VK-1732: optional, last, the absolute crash folder, set once by `LaunchStatusFile::setCrashDirectory` before the first write; older editors never write it). It says `ready` only after the startup scene loaded (a broken scene still gives `ready`, with a warning). The crash filter's `setCrashNotifier` hook and a SIGABRT handler write `failed`. Exit 0 is a normal exit whatever the last state.
- **Lock:** `<.vfproj folder>/.vertexforge/editor.lock` is an exclusive `LockFileEx` on 1 byte at offset 2^32; the content `{"pid":N}` stays readable. `ProjectServiceImpl::setOpenGuard` moves it on every project switch (MCP `project_open`). On read-only media the project opens without it, with a warning. The content browser, the folder tree, the asset migrator, the reference scanner and the game exporter skip `.vertexforge`. It also holds the editor's Play-mode `saves/` and `config.json` (VK-1684: `SaveService`/`ConfigService` take a state folder relative to the `.vfproj`'s folder; the Runtime passes an absolute one, see "Shipped game state").
- **Unicode (VK-1684):** Editor, Runtime and Tests embed `VFEngine/utilities/launch/Utf8CodePage.manifest` (`activeCodePage` UTF-8, listed in their premake `files {}`, merged by link.exe into RT_MANIFEST #1; a new executable must list it too, never put it in an `.rc`). `GetACP()` is 65001, so argv, `getenv`, the CRT's narrow file functions, narrow `std::filesystem` paths and every `*A` call are UTF-8: any `std::string` path is UTF-8 and may hold any character. Bytes that are not valid UTF-8 now make `fs::path(std::string)` throw. Needs Windows 10 1903+ (older Windows ignores it; Editor and Runtime log an error when `launch::processUsesUtf8()` is false). The console's own output code page is switched to UTF-8 by `launch::Utf8ConsoleOutput` (first in each `main`) only when stdout is a console, and restored at exit. The crash dialog (`MessageBoxW`) shows the dump's absolute path; the crash `.txt` is UTF-8 (wide dbghelp). Pinned by `test_unicode_paths` (incl. the built Editor.exe/Runtime.exe manifests and the exporter's icon swap) and `test_save_paths`.
- **Launcher supervision** (VK-1683, `launcher/.../session/`): every launch gets `~/.vertexforge/logs/<project>-<UTC ms>.log` (stdout+stderr through a handle the editor owns, so it is complete even when the launcher exits first; the newest `logRetention` are kept, Settings, default 20, VK-1694) and `<same>.status.json` for `--launch-status` (left out only when the engine's `launchContract < 2` and the ANSI code page cannot encode the path). The command line always puts the project FIRST (older editors take the first argument as the project and ignore unknown flags); `--console` only when the engine's `launchContract >= 1`; `--mcp --mcp-port` per project, never `--mcp-token`. An `EditorSession` polls the status every 250 ms on one daemon "vf-session" thread: Starting → Loading → Ready, "no ready signal" after 15 s without any status, Exited through `Process.onExit()` + one last read. Failures (codes 2-4, crashes, unexplained exits) restore the launcher and show exit code, log tail and the session's crash report: `CrashReports.newestIn` looks in the status line's `crashDir`, else `<working directory>/crashes` (older editors), for `crash_YYYYMMDD_HHMMSS_<pid>.txt` (VK-1732: the crash handler adds the pid, since installed editors share one per-user folder); the session pid's newest report wins, an untagged one (older editor) counts only when none carries it, another pid's never.
- **Project files** (VK-1687): `ProjectConfig::workingDirectory` in memory is always the RESOLVED path (every reader joins onto it). `ProjectServiceImpl` keeps the authored value and its `.vfproj` folder privately (no `ProjectConfig` field: it crosses the plugin boundary). `saveProject` writes: the authored relative value verbatim when saving into the same folder; else a path inside the project, relative (`"."`, which also repairs an old absolute self-path); else an authored absolute path verbatim; else the resolved path. Path containment is `launch/ProjectPathRules.hpp` (`relativeInside`, `liesInside`, `sameFolder`, `starterSceneAllowed`; weakly canonical, lexical where a file system cannot report a final path, case-insensitive; an empty root contains nothing; never `lexically_relative`); MCP's `PathSandbox` shares its `componentEquals`/`isWithin`. The exporter ships an absolute icon path as its file name only. Project Settings Browse stores an inside startup scene or icon relative to the working directory; it refuses an outside startup scene (export packs `Assets/<startupScene>`) and keeps an outside icon absolute. `QueueStartupSceneCommand` (`ScenePersistenceService`; EditorHandler and MCP `project_open`, never the Runtime) queues the startup scene and, when it is missing and is a `.vfScene` inside the `.vfproj` folder outside `.vertexforge`, first builds it: `newScene()` + "Sun" directional light (default-sky angles) + primary "Main Camera", saved in the current format. It creates nothing when the path could not be checked or the scene's `.vfSettings` sidecar still exists (it holds the user's settings); a failed build removes the files it wrote and leaves an empty new scene. It never throws (a warning instead). `newScene()` gives the root a fresh uuid (`clearScene` keeps the root entity).
- **Engine stamp** (VK-1690): after a successful `ProjectServiceImpl::loadProject` with `setStampEngineVersionOnOpen(true)` (set in `EditorServiceBootstrap`; startup and MCP `project_open`; never the Runtime, never after a refused open guard), `ProjectSerialization::stampEngineVersions` rewrites ONLY `engineVersion` (`Version::displayName`) and `assetFormatVersion` (`AssetFormatVersion::toString()`), each NEVER LOWERED: a stored newer `MAJOR.MINOR.PATCH` is kept (absent or unparseable counts as older), so a project an engine has upgraded stays closed to older engines even when an older `Editor.exe` opens it directly. It goes through `ordered_json`: member order, line endings and a BOM are kept, a missing `assetFormatVersion` goes right after `engineVersion`, nothing is written when both already hold what they should, the replace is atomic (`<file>.stamp.tmp`, never left behind), and a read-only file or any failure is a warning (the project still opens). `saveProject` applies the same rule (`engineVersion` against the config's, `assetFormatVersion` against the file it replaces). No `ProjectConfig` field (no plugin API bump).
- **Version-aware open** (VK-1690; launcher `controller/OpenProjectFlow`, `project/VersionCompatibility`, `service/{ProjectBackupService, ProjectCopier, FolderZipWriter, FolderTree, FileJob}`): every Open re-reads the `.vfproj` (with its lock), resolves the engine, then compares the project with that engine's `engine.json`.
  - Rules (first match wins; every newer rule before every older one): no manifest → Unknown; project schema major newer → Newer (editor exit 4); older → Unsupported (exit 3, no migration); project asset format newer → Newer; product `major.minor` newer → Newer; asset format older → Older (re-import); product older → Older; a manifest without schema or asset format, or an unparseable project `engineVersion`/`assetFormatVersion` → Unknown; else Compatible (same or patch-only: opens silently). A `.vfproj` without `assetFormatVersion` reads as 1.0.0 (`LEGACY_ASSET_FORMAT`: every engine before VK-1690).
  - Older → Back up and open (default; Cancel when a backup is impossible) / Open a copy / Open anyway / Cancel. Unknown → one warning per project (raw `RecentEntry` member `unknownVersionWarned`, plus a per-session set). Newer/Unsupported → the engine chooser lists only engines that can open it. The row (`ProjectHealthService.evaluate`) uses the same verdicts: Needs newer (Open disabled) only when no working engine can open the project; OK with a note when only the resolver's engine cannot.
  - Backup: `<parent>/<Folder>-backup-<savedVersion|unknown>-<UTC yyyyMMdd-HHmmss>Z.zip`, written as `.partial`, verified (every entry's size and CRC re-read), renamed with a no-replace `Files.move` (`-2`… on a clash); entries under `<Folder>/`; excludes `.vertexforge` and `<wd>/scripts/compiled` (exactly the template `.gitignore`, pinned by `ProjectContentTest`). Refused when the working directory lies outside the folder, the folder is a drive root, or space is short. The editor starts only after the zip is in place.
  - Copy: beside the original, staged as `.<name>.creating-<uuid>` (the creation infix, which `isStagingFolder` hides), read + write only (never `Files.copy`), same exclusions. The copy's `.vfproj` (`ProjectFileEdit.forCopy`) gets `projectName` = the folder name, and every path member resolved as the editor resolves it (`workingDirectory` against the folder, the others against it) that leads into the original but whose text would not lead to the same place in the copy (absolute, or a `..` that comes back by name) is re-pointed: `workingDirectory` relative, the others relative to the copy's working directory or absolute. Then the copy is refused when one of its members still reaches the original by another spelling (`ProjectCopier.leadsIntoOriginal`: `Files.isSameFile` on the deepest existing folder catches a trailing dot, an admin share, a short name, a link) or is not a path the launcher can read (a trailing space). Its scripts project (`<wd>/scripts/scripts.mtproj`) gets the copy's name too (VK-1695, `ScriptsProjectEdit`: only the bytes inside the root `Name="…"` change; a file mType would not read that way is copied as it is, with a note). It is listed bound to the engine (`RecentProjectsRepository.addBound`), then opened; the original is only read.
  - Version texts: `engineVersion` may carry `VertexForge ` and spaces, tabs, CRs, LFs around it; `assetFormatVersion` must be exactly `MAJOR.MINOR.PATCH`; no leading zeros. Java `VersionNumber.parseProduct`/`parse` and C++ `parseVersionTriple` (ProjectSerialization.cpp) are twins: change both.
  - Backups and copies are `FileJob`s on the "vf-create" thread; shutdown cancels them (`MainController.cancelCreation`).
- **Project templates** (VK-1689; launcher `template/`, engine `assets/templates/<id>/`, pinned by `test_project_templates` and the launcher's `RealEngineContentTest`): the launcher builds a new project from the SELECTED engine's templates and script library, the folders its `engine.json` names; the jar carries no templates (CI fails on a `templates/` entry).

Old `"."` projects keep working.

The library stays byte-identical only until the first open: the asset migration then adds a `.vfmeta` beside every `.mt` and VFX file, which the update ignores.

The creator scans the engine again before writing anything.
- **Script library update** (VK-1691; launcher `scriptlib/` (pure) + `service/ScriptLibraryUpdater`, `ScriptLibraryStatusService`, `controller/ScriptLibraryUpdateFlow`; row menu "Update Script Library…"): brings an existing project's `<wd>/scripts/lib` up to the engine's `scriptLibDir`.

A path that would be a file in one library and a folder in the other is refused. Rules: `LibraryClassifier`, `LibraryPlan`.
  - The new `.vflib.json` records the ENGINE's hashes (never the user's), so a second run is a no-op even after "keep mine"; an up-to-date plan writes no zip, journal or folder (the hold may still create an empty `.vertexforge/editor.lock`).

Any failure, and Open/the next update after a crash, goes through `RecoveryPlanner` (touches only the journal's names; reports whether it finished or undid the update). Refused: editor or another launcher holding the project, wd outside the project folder, `lib` a link/junction, a newer `.vflib.json` format or engine version.
  - The preview lists every file by verdict and warns about game-script imports the update breaks (`ImportCheck`, the Java twin of `test_repo_scan_helpers.hpp`). The row tag ("Library outdated", "missing", "update interrupted") reads only `.vflib.json` against a cached engine index. `scripts/compiled` is left alone: every editor build cleans it first (only Clean Caches deletes it, VK-1695). Flags `FOF_NO_UI | FOFX_RECYCLEONDELETE | FOFX_EARLYFAILURE` (+ `FOFX_ADDUNDORECORD` for the real one), no elevation prompt. External plugins live outside `VFEngine/` under `plugins/<PluginName>/` (e.g. `plugins/PluginAPITest/`, `plugins/HexTerrain/`). Each plugin folder is self-contained:
- carries its own `premake5.lua` (one line: `vfPluginProject("<Name>")` — shared setup in `plugins/plugin_sdk.lua`) — auto-discovered by the root `premake5.lua` under `group "Plugins"`, no root edits needed
- compiles against the exported SDK headers in `sdk/` (NOT engine source) — `premake5 vs2022` auto-refreshes `sdk/` on every run, so **after editing engine headers re-run premake before building plugins**
- ships a `<PluginName>.vfplugin` descriptor (JSON) alongside the DLL
- copies its DLL back into `plugins/<PluginName>/` via postbuild, where `PluginManager` discovers it at runtime
- out-of-tree development: `premake5 export-sdk` packages `sdk/` (headers + imgui.lib + project template); see `sdk/README.md`

### MCP Server (AI agent control)

The Editor embeds a Model Context Protocol server (`VFEngine/mcp/`, owned by `editor/mcp/EditorMcpHost`) so an AI agent such as Claude Code can build scenes, write and build mType scripts, run Play mode and read logs. It lives in Editor.exe because `EventDispatcher` is per-binary. Transport is Streamable HTTP on **127.0.0.1 only** (`POST /mcp`, one JSON response per request) — stdio is impossible because every `vfLog*` writes to stdout. `GET /mcp` with `Accept: text/event-stream` opens the standalone SSE stream (`transport/EventStreamHub`: at most 2 streams, a 3rd evicts the oldest, 15 s `: keepalive`, chunked) used only for server→client notifications (`notifications/tools/list_changed`); `McpService::stop()` order is `queue.shutdown → hub.close → http.stop`, and the hub mutex is never held during a socket send.

- **Enable**: Preferences > AI / MCP (enable, port, optional bearer token, "Copy Claude Code command"), or per session with `Editor.exe <project> --mcp` / `--mcp-port <n>` / `--mcp-token <t>` (command-line flags are never saved; applying an MCP preference change takes over; a malformed flag exits 2, see "Editor launch contract"). The status bar shows `MCP off` / `MCP :<port>` / `MCP error`.
- **Connect**: `claude mcp add --transport http vertexforge http://127.0.0.1:7878/mcp` (add `--header "Authorization: Bearer <token>"` when a token is set).
- **Adding a tool**: add a `mcp::ToolDef` (name, description, JSON `inputSchema`, handler returning `ToolResult::ok/error`) to the matching `register*Tools` group in `mcp/tools/*.cpp`; new groups are declared in `CoreTools.hpp` and called from `registerCoreTools`. Tools use only Services/Import/Utilities headers and reach the engine through `EventDispatcher`.
  - **Affinity**: `ThreadAffinity::Main` (default) runs the handler on the editor main thread inside `EditorMcpHost::drain()` — required for anything touching EventDispatcher handlers, EnTT or ImGui. `ThreadAffinity::Worker` runs on the HTTP connection thread and is only for filesystem/long work (script writes, imports); such a handler must wrap every dispatcher call in `context.runOnMain(...)`. Raise `timeout` for long tools (build/import).
  - **Drain placement** (VK-1653): `EditorHandler`'s frame callback drains MCP FIRST, before `frameTaskGraph->execute()`, because only there is the render thread idle (`MainLoop` already waited in `beginFrame()`; the graph's `Render` task wakes it via `FrameSynchronizer::endFrame()`, after which it walks EnTT and the terrain grids). Never move the drain after `execute()`. Corollary: a Main tool must never wait for a rendered frame — nothing renders until the drain returns; only Worker tools poll across frames (`viewport_screenshot`, `terrain_generate_heightmap`).
  - **Capture by value**: handlers outlive the `register*Tools` call, and a main-thread task can still run after its caller timed out, so handler and `runOnMain` lambdas capture the `ToolContext`, arguments and any other state BY VALUE — never `[&]`.
  - Bad arguments throw `ArgError` from `ArgReader` helpers and engine failures throw or return `ToolResult::error`; both reach the agent in-band as `isError:true` results. Only a main-thread timeout is a JSON-RPC error (-32001).
  - **Images**: return `ToolResult::image(base64, "image/png", structured)`; the block is appended after the text block. `mcp/util/ImageEncode` holds the half→RGBA8, downscale, PNG (the Mcp copy of `stb_image_write`, static) and base64 helpers. `viewport_screenshot` polls `RequestViewportReadbackCommand` / `TakeViewportReadbackQuery` (GPU copy recorded in `OffScreenViewPort::render`, completed after that frame slot's fence).
  - **Editor-only tools** that need editor objects (e.g. `camera_*` on `EditorCamera`) are registered from `EditorMcpHost::init()` after `registerCoreTools`, not in `mcp/tools/`.
  - **Undo**: every entity/component/`material_assign` mutation records `mcp/undo` commands through `UndoRecorder`, which pushes ONE `BatchUndoCommand` via `PushUndoableCommand` after the edit succeeds. Never dispatch `BeginBatchCommand`/`EndBatchCommand` from MCP — an async file operation may hold the batch open. Re-created entities get new entt ids; undo commands store original ids and resolve them through `EntityIdRemap` (cleared on `SceneClearedNotification`). `.vfAnimator` edits are the one asset exception: they ARE undoable through the hash-guarded `AnimatorAssetUndo` (see Animation tools). Asset creation (`material_create`, a new `.vfAnimator`) and the other asset, script, scene, play and camera tools are not undoable.
  - **Plugin components** are reached through the JSON events in `services/events/scene/PluginComponentEvents.hpp` (handled by `editor/handlers/PluginComponentHandler`, strict patching via `utilities/serialization/MetaFieldPatch.hpp`). Never copy-construct the `meta_any` returned by `bridge.metaType.from_void(ptr)` — the copy is owning and writes are lost.

### Services Layer

The `services/` module provides decoupled communication via CQRS pattern:

```cpp
// Commands - execute actions, may return results
events::EventDispatcher::instance().execute(SomeCommand{args});

// Queries - read-only data retrieval
auto result = events::EventDispatcher::instance().query(SomeQuery{});

// Notifications - fire-and-forget broadcasts (pub/sub)
events::EventDispatcher::instance().publish(SomeNotification{data});

// Subscribe to notifications
auto token = dispatcher.subscribe<SomeNotification>([](const auto& n) { ... });
dispatcher.unsubscribe(token);
```

Event types are defined in `services/events/` (e.g., `ResourceEvents.hpp`, `SceneEvents.hpp`, `PreviewEvents.hpp`).

### Provider/Adapter Pattern

Services define **provider interfaces** that abstract engine capabilities:

```cpp
// In services/providers/IPreviewProvider.hpp
class IPreviewProvider {
    virtual void initMaterialPreview(void* instanceId) = 0;
    virtual void* renderMaterialPreview(void* instanceId) = 0;
    // ...
};
```

Core implements these via **adapters** that wrap internal controllers:

```cpp
// In core/adapters/PreviewAdapter.hpp
class PreviewAdapter : public services::IPreviewProvider {
    std::unordered_map<void*, std::unique_ptr<MaterialPreviewController>> materialControllers;
    // Implements interface by delegating to controllers
};
```

**Multi-instance support**: Preview services use `void* instanceId` (typically `this` pointer of window) to manage independent controller instances per editor window.

### Bootstrap Pattern

Editor and Runtime use bootstrap classes to initialize the engine:

```cpp
// Editor initialization flow
EditorHandler::init() {
    bootstrap = std::make_unique<EditorBootstrap>();
    bootstrap->init();  // Creates Core, Graphics, Adapters

    // Get providers from bootstrap, pass to services
    auto previewService = std::make_shared<PreviewServiceImpl>(bootstrap->getPreviewProvider());
    previewService->registerEventHandlers();
}
```

This encapsulates all Core/Graphics dependencies within bootstrap, keeping Editor/Runtime clean.

### Import Pipeline

Asset imports flow through a staged pipeline (`import/pipeline/`):

```
File → HeaderValidationStage → FileTypeDetectionStage → FileProcessingStage → .vf* output
```

Each asset type (Mesh, Texture, Audio) has a processor in `import/types/` with progress callback support:
```cpp
using MeshProgressCallback = std::function<void(float progress)>;
meshProcessor.loadFromFile(file, fileName, location, progressCallback);
```

## Naming Conventions

- **Classes/Files**: PascalCase, matching names (`CoreInterface.hpp` contains `class CoreInterface`)
- **Variables**: camelCase
- **Namespaces**: lowercase (`core::`, `controllers::`, `components::`, `scene::`, `resource::`, `services::`)
- **Suffixes**:
  - `*Controller` - Internal facade within module
  - `*Handler` - Orchestrator coordinating subsystems
  - `*Adapter` - Implements provider interface, wraps controllers
  - `*Provider` - Interface prefix (`I*Provider`)
  - `*Service` - Interface prefix (`I*Service`)
  - `*ServiceImpl` - Service implementation
  - `*Bootstrap` - Initialization orchestrator
  - `*Manager`, `*System`, `*Component`, `*Generator` - Other common patterns

## Custom Asset Formats

`.vfImage`, `.vfHdr`, `.vfMesh`, `.vfAudio`, `.vfAnim`, `.vfImposter`, `.vfWorld` - Binary formats for engine-processed assets.

The shared header of `.vfImage`/`.vfHdr`/`.vfMesh`/`.vfAnim`/`.vfAudio` carries `AssetFormatVersion` (`Config.hpp`, 1.0.0, exact match via `AssetFormatVersion::matches`), never the engine `Version` (VK-1680). Writers, plugin importers included, stamp `AssetFormatVersion::*`. Bump it ONLY when that binary layout changes: a bump invalidates every asset on disk. `test_asset_format_version` loads hand-built 1.0.0 files and scans `VFEngine/` + `plugins/` so that only the tests read `Version::major/minor/patch`. Fonts, terrain, sectors etc. own their own format versions.

## Adding New Features

### New ECS Component
1. Add struct to `utilities/components/Components.hpp`
2. Use via `Entity::addComponent<T>()` / `Entity::getComponent<T>()`

### New Asset Type
1. Create loader in `import/types/`
2. Add pipeline stage in `import/pipeline/stages/`
3. Define resource type in `utilities/resource/Types.hpp`

### New Editor Window
1. Create class in `editor/windows/`
2. Register in `WindowImguiHandler`
3. Use `EventDispatcher` to access engine functionality (never include Core/Graphics directly)

### New Editor Tool (DLL-backed, e.g., ProceduralGen, ImageProcessing)
1. Create DLL subsystem under `utilities/<toolname>/` with export header (`VF_<NAME>_BUILD_DLL` / `VF_<NAME>_API`)
2. Add SharedLib project to `premake5.lua` in "Subsystems" group, add `removefiles` to Utilities, link from Editor
3. Postbuild: copy DLL to `bin/Editor/{Debug,Release}/x64/`
4. Create editor window in `editor/windows/<toolname>/` — member of `MainImguiWindow`, toggled via `show()` from `MainMenuBar`
5. Add to `handleToolsMenu()` in `MainMenuBar.cpp`
6. Wire into `MainImguiWindow.hpp/cpp`: include, member, setter, `draw()` call
7. For async work: use `std::async` + `std::future`, poll in `draw()`. Wait for futures in destructor to avoid dangling pointers
8. For GPU preview: use `LoadEditorTextureFromDataCommand` / `ReleaseEditorTextureCommand`. Update preview BEFORE `ImGui::Image()` (not after) to avoid invalid descriptor sets
9. Export via `nfd::FileDialog::saveFileDialog()` + `.vfmeta` sidecar via `AssetMetadataSerializer`

### New Service
1. Create interface in `services/interfaces/I<Name>Service.hpp`
2. Create provider interface in `services/providers/I<Name>Provider.hpp`
3. Create implementation in `services/impl/<Name>ServiceImpl.hpp/cpp`
4. Create events in `services/events/<Name>Events.hpp`
5. Create adapter in `core/adapters/<Name>Adapter.hpp/cpp`
6. Wire up in bootstrap classes (`EditorBootstrap`, `RuntimeBootstrap`)

### New External Plugin
1. Create `plugins/<PluginName>/<PluginName>.cpp` implementing `IPlugin` (see `VFEngine/plugin/api/IPlugin.hpp`); export via `VF_PLUGIN_EXPORT` macros from `PluginExport.hpp`
2. Author `plugins/<PluginName>/<PluginName>.vfplugin` (JSON descriptor: name, version, entry, dependencies — parsed by `PluginDescriptor`)
3. Add `plugins/<PluginName>/premake5.lua` containing just `vfPluginProject("<PluginName>")` (+ `links { "imgui" }` if it has editor UI) — all common setup lives in `plugins/plugin_sdk.lua`. The root `premake5.lua` auto-discovers it — just re-run `premake5 vs2022`
4. `PluginManager` discovers and loads it from `plugins/` at editor startup; subscribe to engine events via `PluginEventBus` / `PluginContext`
   - Roots (VK-1732, `PluginLoadConfig`, pure logic in `plugin/core/PluginRoots.hpp`, pinned by `test_plugin_roots`): the dev tree and the Runtime load one root (`resolvePluginsDirectory()`, scanned recursively), and a Plugin Manager toggle edits the `.vfplugin` in place (`descriptorTextWithEnabled` in `utilities/export/PluginDescriptorEdit.hpp` keeps member order, BOM, CRLF and the final newline). An installed engine (`stateLocation` `"user"`) also loads `Documents\VertexForge\Plugins\<Folder>\*.vfplugin` (top level only), keeps toggles of SHIPPED plugins in `~/.vertexforge/editor/plugin-overrides.json` (`{"version":1,"enabled":{name:bool}}`; an Invalid or Newer file is ignored and never rewritten; Reset removes an entry) and plugin data in `~/.vertexforge/editor/plugin-data/<Name>`. Two plugins with one name never both load: the shipped one (else the first by path) wins, the other is "Shadowed".
   - New Plugin in an installed engine scaffolds a Standalone project (`scaffold::Flavor::Standalone`): its own premake workspace against the install's `sdk/` (`VERTEXFORGE_SDK` overrides), ONE configuration (the editor's own, for the ABI), and a postbuild copy of the DLL beside the `.vfplugin`. The dev tree keeps the in-tree `vfPluginProject` flavour.
   - Export (VK-1733): `ExportHandler` hands the exporter both roots' non-shadowed plugins with their effective enabled state (`ExportConfig::pluginSources`), and every shipped descriptor is written with `"enabled": true` (its manifest hash is that of the shipped bytes).
5. Custom shaders/geometry: `ctx->createCustomPipeline` / `uploadCustomMesh` / `drawCustomMesh` (graphics capability). Editor UI: implement `ImguiWindow`, `links { "imgui" }`, `ImGui::SetCurrentContext(ctx->getImGuiContext())`, then `ctx->registerEditorWindow(window, "Title")` — titled windows appear in the editor's Plugins menu
6. AI agent tools (editor capability): `ctx->registerMcpTool({name, title, description, inputSchema, readOnly, destructive, timeoutMs, handler})` — see `plugins/PluginAPITest` (`pluginapitest_echo`). The `.vfplugin` `apiVersion` must equal `VF_PLUGIN_API_VERSION` exactly
